# Platform Portability

Use this reference when adapting the engineering exploration workflow to another AI coding assistant, IDE, agent framework, or local automation platform.

## Contents

- Core Rule
- Known Platform Mapping
- Platform Families
- Adapter Checklist
- Common Pitfalls

## Core Rule

Do not duplicate the whole workflow for every platform. Keep one portable core and create thin adapters.

Portable core:

- purpose: help the user explore engineering ideas before implementation
- triggers: brainstorming, architecture, technical tradeoff, feature/module design, "先不写代码", "不要修改代码"
- boundaries: no file edits, scaffolding, or modifying commands until explicit authorization
- output contract: clarify requirements, compare options, define architecture/interface/data flow/security/errors/tests/risks
- implementation gate: switch to coding only after the user clearly asks to implement

Platform adapter:

- where the instruction lives
- how it is triggered
- whether it is always loaded, manually invoked, or agent-requested
- which tools or filesystem actions are available
- how permissions, memory, commands, and references are represented
- how to test whether it actually takes effect

## Known Platform Mapping

Use these mappings as starting points, then verify the current platform documentation before installing because AI IDE rule formats change quickly.

| Platform | Best adapter shape | Notes |
| --- | --- | --- |
| Codex | Skill package | Keep `SKILL.md` at the skill root, use `agents/openai.yaml` for UI metadata, and put longer guidance in `references/`. |
| CodeBuddy | Skill, Rule, Subagent, or `CODEBUDDY.md` | Use `.codebuddy/skills/<name>/SKILL.md` for automatically selected specialized capability, `.codebuddy/rules/*.md` for persistent behavior, `.codebuddy/agents/*.md` for dedicated modes with tool permissions, and `CODEBUDDY.md` for broad repository guidance. |
| Work Buddy | Direction, workflow, capability, or memory | Model the exploration behavior as a direction, larger planning as a workflow, reusable checks as capabilities, and user preference as memory. Keep consent gates explicit because workflows can coordinate multi-step action. |
| Trae | Markdown rule | Use the project rule path generated by the current IDE version, commonly `.trae/project_rules.md` or `.trae/rules/project_rules.md`, or the platform's user-level rules for personal preferences. Keep the rule compact and include Chinese trigger phrases for bilingual work. |
| Cursor / Windsurf | Markdown rule | Use project rules for repository conventions and user/global rules for personal collaboration preferences. |
| Claude Code | Project instruction, command, or skill-like package when supported | Use a project instruction for default behavior and a command for manually invoked exploration sessions. |
| GitHub Copilot | Repository instruction or agent skill when supported | Use repository instructions for broad behavior; use skills only when the environment supports agent skill packages. |
| Gemini CLI / other agents | Instruction file or extension metadata | Put the portable core in Markdown and keep platform metadata thin. |

When a platform supports multiple mechanisms, choose the smallest one that preserves the behavior:

- Need automatic behavior during normal chat: rule or project instruction.
- Need manual user control: command.
- Need isolated context or specialized tools: subagent or workflow.
- Need reusable callable operation: capability or skill.

## Platform Families

### Skill Package Platforms

Use this shape when the platform supports a `SKILL.md` style package.

Examples: Codex skills, CodeBuddy skills, and similar agent skill systems.

Recommended adapter shape:

```text
engineering-exploration/
├── SKILL.md
├── references/
└── agents/ or platform metadata when supported
```

Keep `SKILL.md` concise: trigger, behavior boundary, output contract, and links to references. Put detailed checklists in `references/`.

For CodeBuddy-style skill directories, place the package under `.codebuddy/skills/engineering-exploration/` for project-level use, or the user-level skills directory for personal reuse.

### Rule-Based AI IDEs

Use this shape when the platform supports persistent Markdown rules.

Examples: Trae `.rules` / project rules, CodeBuddy rules, Cursor rules, Windsurf rules, and similar IDE rule systems.

Recommended rule content:

```markdown
# Engineering Exploration Rule

Apply this rule when the user is exploring a software engineering idea before implementation.

- Stay in exploration mode for brainstorming, architecture, feature/module design, tradeoff analysis, and implementation planning.
- Do not create files, edit files, scaffold projects, or run modifying commands unless the user explicitly asks to implement.
- If the user's intent is ambiguous, ask whether to continue refining the design or begin implementation.
- Produce concrete engineering outputs: requirements, options, recommendation, module boundaries, interfaces, data flow, security risks, error handling, tests, and rollout notes when relevant.
```

Use project-level rules for team/project conventions. Use user-level rules for personal collaboration preferences such as "do not implement during brainstorming".

For Trae-style rules, prefer the project-level rule file generated by the IDE when the behavior should travel with the repository. Public examples commonly show either `.trae/project_rules.md` or `.trae/rules/project_rules.md`; use the path your installed Trae version creates. Use user-level rules only for personal preference, because not every collaborator will share them.

For CodeBuddy-style rules, prefer `.codebuddy/rules/engineering-exploration.md` when the behavior should always be loaded as project memory.

### Project Instruction Files

Use this shape when the platform reads a project instruction file.

Examples: `AGENTS.md`, `CODEBUDDY.md`, `CLAUDE.md`, or similar project root instruction files.

Recommended placement:

```markdown
## Engineering Exploration

When the user is discussing requirements, architecture, design, technical choices, or implementation plans, stay in exploration mode until explicit implementation authorization.
```

This is best for a broad project default. Keep it short so it does not crowd out repository-specific build, test, and style instructions.

For CodeBuddy-style broad project guidance, use `CODEBUDDY.md` only for short defaults. Put longer reusable guidance in rules or skills.

### Commands And Slash Commands

Use this shape when the platform supports custom commands.

Examples: CodeBuddy custom slash commands, Claude/Cursor-style command prompts, or local command palettes.

Recommended command:

```text
/explore-engineering
```

Command behavior:

- summarize the user's idea
- ask only high-impact clarification questions
- compare 2-4 options when direction is open
- produce an implementation-ready plan
- stop before editing files unless the user explicitly asks to continue into implementation

Commands are useful when the user wants manual control instead of automatic triggering.

### Agent Or Workflow Platforms

Use this shape when the platform models work as capabilities, workflows, directions, or subagents.

Examples: Work Buddy-style capabilities/workflows/directions, CodeBuddy subagents, local agent frameworks, or enterprise assistants.

Recommended unit split:

- Directions: the exploration behavior and consent gate.
- Workflow: optional multi-step planning flow for larger features.
- Capability: optional reusable operation such as "produce implementation plan" or "review design risks".
- Memory: optional user preference that exploration should precede implementation.

Keep approval gates explicit. Workflow platforms often can act proactively, so the instruction must preserve user control over file edits and commands.

For CodeBuddy-style subagents, use a read-only or planning-oriented agent when available, and avoid giving broad editing tools to an exploration-only agent.

For Work Buddy-style units, put the consent rule in directions, make the multi-step design process a workflow only when needed, and reserve capabilities for reusable operations like "compare architecture options" or "audit implementation risks".

## Adapter Checklist

Before declaring a platform adapter complete, verify:

- The trigger terms include both English and Chinese phrases when the user works bilingually.
- The platform-specific file path and format are correct.
- The adapter says what not to do before authorization.
- The adapter names the exact confirmation point before implementation.
- The adapter can still hand off to normal coding once the user explicitly asks.
- Large details live in references or linked docs instead of the always-loaded rule.
- The test prompts cover exploration, ambiguous momentum, explicit implementation, and a non-exploration coding request.

## Common Pitfalls

- Do not treat every platform as a Skill system. Some use rules, project instructions, commands, memories, or workflows.
- Do not make the rule always-on if it would block urgent bug fixing or direct implementation requests.
- Do not copy platform-private metadata into the portable core.
- Do not let "no code during exploration" become "never code".
- Do not omit domestic platform formats; many use Markdown rules, project/user scopes, custom commands, memory, or workflow units rather than Codex-style `agents/openai.yaml`.
